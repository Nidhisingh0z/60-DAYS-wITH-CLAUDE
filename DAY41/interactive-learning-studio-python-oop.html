Module 1 / 4

Classes & Objects: The Foundations

Every OOP concept in Python builds on one idea: a class is a blueprint, and an object is a specific thing built from that blueprint.

🏗️
AnalogyA class is like an architect's blueprint for a house — it specifies "has 3 bedrooms, has a door, can lock()". The blueprint itself isn't a house you can live in. Each house actually built from it — 12 Oak Street, 4 Maple Ave — is an object: a real instance with its own address, paint color, and furniture, but built to the same plan.

Defining a class

A class bundles data (attributes) and behavior (methods) together. The special __init__ method runs automatically when a new object is created — it's the constructor.

pythonclass Dog: # __init__ runs once, when Dog(...) is called def __init__(self, name, breed): self.name = name # instance attribute self.breed = breed self.energy = 100 def bark(self): return f"{self.name} says Woof!" # Two objects built from the same class rex = Dog("Rex", "Labrador") mochi = Dog("Mochi", "Shiba Inu") print(rex.bark()) # Rex says Woof! print(mochi.name) # Mochi

self is not a keyword — it's just the conventional name for the first parameter of every instance method, and it refers to the specific object the method was called on. rex.bark() is really Python calling Dog.bark(rex) behind the scenes.

Procedural vs. object-oriented

Procedural approach
  • Data lives in separate variables or dicts.
  • Functions take data in as arguments every time.
  • Related data and behavior can drift apart as the program grows.
Object-oriented approach
  • Data and the functions that act on it live together in one class.
  • Methods access data via self — no need to pass it around.
  • New "kinds of things" are added by defining new classes, often reusing old ones.

Common misconceptions

✗ "A class and an object are basically the same thing."
✓ A class is a definition; an object is a concrete thing built from it. You can create thousands of objects from one class.
✗ "self is a special Python keyword."
✓ self is just a parameter name (convention, not syntax) that refers to the current instance. You could technically call it anything.
✗ "Every class must define __init__."
✓ If you omit it, Python uses a default no-op constructor. You only need __init__ when the object needs setup data.

Key takeaways

  • A class defines structure and behavior; an object is a specific instance of that structure.
  • __init__(self, ...) runs automatically on creation to set up instance attributes.
  • Each object has its own copy of instance attributes, even though they share one class definition.
  • self is how a method reaches back into the specific object it was called on.
Module 2 / 4

The Four Pillars of OOP

Encapsulation, inheritance, polymorphism, and abstraction aren't abstract theory — they're four practical answers to "how do I keep a growing codebase manageable?"

1. Encapsulation — protecting internal state

Encapsulation bundles data with the methods that are allowed to touch it, and hides the messy internals behind a clean interface. Python signals intent with naming conventions rather than hard enforcement.

pythonclass BankAccount: def __init__(self, balance): self._balance = balance # "protected": please don't touch directly def deposit(self, amount): if amount <= 0: raise ValueError("Deposit must be positive") self._balance += amount @property def balance(self): # read-only view return self._balance
🎛️
AnalogyEncapsulation is a vending machine: you press buttons (the public methods), but you never reach inside to rearrange the coils yourself. The machine controls its own internals and only exposes a safe interface.

2. Inheritance — reusing and specializing

A subclass inherits attributes and methods from a parent class, and can override or extend them. super() calls the parent's version so you're not duplicating logic.

pythonclass Animal: def __init__(self, name): self.name = name def speak(self): return f"{self.name} makes a sound" class Cat(Animal): # Cat inherits from Animal def speak(self): # override base = super().speak() return f"{base} — specifically, a meow"

3. Polymorphism — one interface, many shapes

Polymorphism means different objects can respond to the same method call in their own way. Python leans on duck typing: "if it walks like a duck and quacks like a duck" — you don't need a shared base class, just a matching method name.

pythonfor animal in [Cat("Tom"), Dog("Rex")]: print(animal.speak()) # each runs its OWN speak()
🔌
AnalogyPolymorphism is a universal power socket: you plug in a lamp, a laptop, or a fan — all different devices — and each responds to "power on" in its own way, through the same interface.

4. Abstraction — hiding complexity behind an interface

Abstraction defines what a family of classes must do, without dictating how. Python's abc module lets you declare abstract methods that subclasses are forced to implement.

pythonfrom abc import ABC, abstractmethod class Shape(ABC): @abstractmethod def area(self): ... # no implementation here class Circle(Shape): def __init__(self, r): self.r = r def area(self): return 3.14159 * self.r ** 2 # Shape() would raise TypeError — it's incomplete on purpose

Common misconceptions

✗ "Double underscore (__balance) makes an attribute truly private."
✓ It triggers "name mangling" (becomes _ClassName__balance) to avoid accidental clashes in subclasses — it's obfuscation, not real access control.
✗ "Polymorphism requires inheritance."

Key takeaways

  • Encapsulation hides internal state behind methods and properties you control.
  • Inheritance lets a subclass reuse and override behavior from a parent via super().
  • Polymorphism means the same method name can behave differently across object types.
  • Abstraction (via ABC) forces subclasses to implement a required interface.
Module 3 / 4

Dunder Methods, Class Methods & Composition

This module moves from "how do I define a class" to "how do I make a class feel like a natural part of the language" — plus how to combine objects without always reaching for inheritance.

Dunder (magic) methods

Methods surrounded by double underscores are hooks Python calls automatically for built-in operations: printing, equality, length, addition, and more.

pythonclass Vector: def __init__(self, x, y): self.x, self.y = x, y def __repr__(self): # dev-facing string return f"Vector({self.x}, {self.y})" def __add__(self, other): # enables v1 + v2 return Vector(self.x + other.x, self.y + other.y) def __eq__(self, other): # enables v1 == v2 return (self.x, self.y) == (other.x, other.y) v1, v2 = Vector(1, 2), Vector(3, 4) print(v1 + v2) # Vector(4, 6) — via __add__
🎮
AnalogyDunder methods are like a universal remote's standard buttons. Every remote (object) can wire up its own behavior to "power", "volume up", "+" — Python just presses the button (+, print(), ==) and lets your class decide what happens.

Instance vs. class variables

Instance variable
  • Set on self, usually in __init__.
  • Every object gets its own separate copy.
  • Example: each Dog's own name.
Class variable
  • Defined directly in the class body, shared by all instances.
  • Good for constants or counters shared across objects.
  • Example: Dog.species_count tracked once for all dogs.
pythonclass Dog: species_count = 0 # class variable — shared def __init__(self, name): self.name = name # instance variable — per object Dog.species_count += 1 @classmethod def total_dogs(cls): # receives the CLASS, not an instance return cls.species_count @staticmethod def is_valid_name(name): # receives nothing extra — a plain utility return len(name) > 0

Composition: "has-a" instead of "is-a"

Inheritance models "is-a" relationships (a Cat is an Animal). Composition models "has-a" relationships — building complex objects out of simpler ones as attributes, instead of a class hierarchy.

pythonclass Engine: def start(self): return "Engine roaring" class Car: def __init__(self): self.engine = Engine() # Car HAS an Engine, isn't one def start(self): return self.engine.start()

Common misconceptions

✗ "Class variables always act like other languages' static fields."
✓ Assigning to self.attr on an instance creates a new instance attribute that shadows the class one — mutating a shared mutable class variable (like a list) in place is a common bug source.
✗ "@staticmethod still needs a self parameter."
✓ Static methods take no automatic first argument at all — they're just regular functions namespaced inside the class.

Key takeaways

  • Dunder methods let your objects work naturally with print(), +, ==, len(), and more.
  • Instance variables belong to one object; class variables are shared across every instance.
  • @classmethod receives the class; @staticmethod receives nothing extra.
  • Composition ("has-a") is often more flexible than inheritance ("is-a") for combining behavior.
Module 4 / 4

Multiple Inheritance, MRO & Mastery

The final module tackles the parts of Python OOP that trip up even experienced developers: multiple inheritance, the diamond problem, and how Python actually resolves which method to call.

Multiple inheritance & the diamond problem

Python allows a class to inherit from more than one parent. This is powerful, but creates ambiguity when two parents define the same method — known as the diamond problem.

pythonclass A: def greet(self): return "A" class B(A): def greet(self): return "B" class C(A): def greet(self): return "C" class D(B, C): pass print(D().greet()) # "B" — see MRO below print(D.__mro__) # (D, B, C, A, object)

Python resolves this with the C3 linearization algorithm, exposed as ClassName.__mro__. In short: a class always appears before its parents, and left-to-right declaration order among siblings is preserved — but it's smarter than plain depth-first search, since it guarantees every class appears only once and keeps a consistent order across the whole hierarchy.

Mixins: composition-flavored inheritance

A mixin is a small class designed to be combined with others to add one specific capability — not to stand alone.

pythonclass JSONExportMixin: def to_json(self): import json return json.dumps(vars(self)) class User(JSONExportMixin): def __init__(self, name): self.name = name print(User("Ada").to_json()) # {"name": "Ada"}
🍳
AnalogyMRO is a family reunion's seating algorithm: it makes sure every relative sits exactly once, closer relatives sit before more distant ones, and the order stays consistent no matter which side of the family you ask. Mixins are like recipe add-ins — a "chocolate chip mixin" isn't a dessert on its own, it flavors whatever base it's added to.

Inheritance vs. composition vs. mixins

Use inheritance when…
  • There's a genuine "is-a" relationship.
  • Subclasses should share a stable, evolving interface.
Use composition/mixins when…
  • You want to reuse behavior across unrelated classes.
  • You want to avoid deep, fragile hierarchies.

Common misconceptions

✗ "Multiple inheritance is always bad practice."
✓ It's risky when hierarchies get deep and tangled, but small, focused mixins are a widely-used, safe pattern.
✗ "MRO is just simple left-to-right, depth-first search."
✓ Python uses C3 linearization, which is stricter — it guarantees a class never appears before its own subclasses and produces a single consistent order, which plain depth-first search can't always do.

Key takeaways

  • Python resolves multiple-inheritance conflicts using the deterministic C3 linearization MRO.
  • ClassName.__mro__ lets you inspect the exact method lookup order.
  • Mixins add one focused capability to otherwise unrelated classes.
  • Prefer composition or mixins over deep inheritance trees when relationships aren't truly "is-a".

Final practical challenge

Build a tiny library system using everything from this tutorial:

  • An abstract LendableItem base class (abstraction) with an abstract describe() method.
  • Book and DVD subclasses (inheritance) that override describe() (polymorphism).
  • A _is_checked_out attribute controlled only through check_out()/return_item() methods (encapsulation).
  • A Library class that has a list of items (composition), plus a class variable tracking the total number of libraries created.
  • __repr__ and __len__ on Library so print(library) and len(library) work naturally.
pythonfrom abc import ABC, abstractmethod class LendableItem(ABC): def __init__(self, title): self.title = title self._is_checked_out = False @abstractmethod def describe(self): ... def check_out(self): if self._is_checked_out: raise ValueError("Already checked out") self._is_checked_out = True def return_item(self): self._is_checked_out = False class Book(LendableItem): def __init__(self, title, author): super().__init__(title) self.author = author def describe(self): return f"'{self.title}' by {self.author}" class DVD(LendableItem): def __init__(self, title, runtime): super().__init__(title) self.runtime = runtime def describe(self): return f"'{self.title}' ({self.runtime} min)" class Library: total_libraries = 0 def __init__(self, name): self.name = name self.items = [] # composition: Library HAS items Library.total_libraries += 1 def add_item(self, item): self.items.append(item) def __len__(self): return len(self.items) def __repr__(self): return f"Library('{self.name}', {len(self)} items)"

Summary notes

A class is a blueprint; an object is an instance built from it, with its own state set up in __init__. The four pillars — encapsulation, inheritance, polymorphism, abstraction — give you tools to hide internals, reuse behavior, respond flexibly to the same call, and enforce a required interface. Dunder methods make your objects feel native to Python, while @classmethod/@staticmethod and instance-vs-class variables control where behavior and state actually live. Composition and mixins offer flexible alternatives to deep inheritance chains, and Python's C3-linearization MRO deterministically resolves method lookups even in multiple-inheritance diamonds. Reach for inheritance for genuine "is-a" relationships, and composition for everything else.
